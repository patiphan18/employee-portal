| สถานะ | อนุมัติให้พัฒนา |

## 1. ภาพรวม

Employee Portal คือเว็บแอปพลิเคชันที่ให้พนักงานดูและดูแลข้อมูลโปรไฟล์ของตนเองได้
ข้อมูลที่เป็นตัวตนตามทะเบียน (ชื่อและนามสกุล) เป็นกรรมสิทธิ์ของฝ่ายบุคคล จึงกำหนดให้อ่านอย่างเดียว
ส่วนข้อมูลที่พนักงานดูแลเองได้ ได้แก่ รูปโปรไฟล์ ข้อมูลติดต่อ และทักษะ สามารถแก้ไขได้
และทุกการเปลี่ยนแปลงจะถูกบันทึกเป็นประวัติที่ตรวจสอบย้อนหลังได้

### 1.1 เป้าหมาย

- **G1** — พนักงานเห็นข้อมูลโปรไฟล์ของตนเองครบถ้วนในหน้าเดียว
- **G2** — พนักงานแก้ไขรูปโปรไฟล์ ข้อมูลติดต่อ และทักษะได้เอง โดยไม่ต้องผ่านฝ่ายบุคคล
- **G3** — ทุกการแก้ไขถูกบันทึกและพนักงานดูย้อนหลังได้ตามช่วงเวลาที่ตั้งค่าไว้ (ค่าเริ่มต้น 7 วัน)
- **G4** — หน้าจอใช้งานได้ดีทั้งบนมือถือ แท็บเล็ต และเดสก์ท็อป
- **G5** — ต้องยืนยันตัวตนก่อนเข้าใช้งาน และผู้ใช้ต้องไม่สามารถอ่านหรือแก้ไขโปรไฟล์ของผู้อื่นได้

### 1.2 สิ่งที่อยู่นอกขอบเขต

- การจัดการข้อมูลหลักของฝ่ายบุคคล (การจ้างงาน การพ้นสภาพ เงินเดือน)
- ผังองค์กรและสายการบังคับบัญชา
- การเชื่อมต่อ SSO / SAML / OIDC (เวอร์ชัน 1 ใช้ JWT กับบัญชีภายในเท่านั้น)
- การแจ้งเตือนทางอีเมลหรือ push notification

### 1.3 คำศัพท์

| คำศัพท์ | ความหมาย |
|---|---|
| โปรไฟล์ (Profile) | ข้อมูลที่พนักงานเห็น ได้แก่ ชื่อ-นามสกุล รูปโปรไฟล์ ข้อมูลติดต่อ และทักษะ |
| ข้อมูลติดต่อ (Contact block) | หมายเลขโทรศัพท์มือถือ อีเมล และที่อยู่ ซึ่งแก้ไขแยกจากกันได้ |
| คลังทักษะ (Skill catalog) | รายการทักษะที่ผู้ดูแลระบบตั้งค่าได้ ให้พนักงานเลือก เช่น Go, React |
| ทักษะส่วนตัว (Custom skill) | ทักษะที่พนักงานพิมพ์เพิ่มเองเพราะไม่มีในคลัง อยู่เฉพาะในโปรไฟล์ของคนนั้น ไม่ปรากฏต่อผู้อื่น |
| รายการเปลี่ยนแปลง (Change event) | หนึ่งแถวในประวัติ ที่อธิบายการแก้ไขข้อมูลหนึ่งฟิลด์ |
| ช่วงเวลาย้อนหลัง (Retention window) | ระยะเวลาที่แสดงประวัติย้อนหลัง ตั้งค่าได้ ค่าเริ่มต้น 7 วัน |

## 2. ผู้ใช้งานระบบ

| ผู้ใช้งาน | คำอธิบาย | สิทธิ์ |
|---|---|---|
| พนักงาน (Employee) | พนักงานที่ยืนยันตัวตนแล้ว | ดู/แก้ไขโปรไฟล์ของตนเอง ดูประวัติของตนเอง ย้อนกลับการแก้ไขของตนเอง |
| ผู้ดูแลระบบ (Admin) | บัญชีที่มี role เป็น `admin` | จัดการคลังทักษะและการตั้งค่าระบบ **เท่านั้น** ไม่มีโปรไฟล์พนักงานและเข้าถึง `/me*` ไม่ได้ |
| ผู้ที่ยังไม่ล็อกอิน | ผู้เข้าชมที่ยังไม่ยืนยันตัวตน | เข้าสู่ระบบได้อย่างเดียว |

## 3. ข้อกำหนดเชิงหน้าที่ (Functional Requirements)

### FR-1 — การยืนยันตัวตน

| รหัส | ข้อกำหนด |
|---|---|
| FR-1.1 | ผู้ใช้เข้าสู่ระบบด้วยอีเมลและรหัสผ่าน |
| FR-1.2 | รหัสผ่านถูกเก็บเป็น bcrypt hash (cost ไม่ต่ำกว่า 10) ไม่มีการเก็บหรือบันทึก log รหัสผ่านแบบข้อความธรรมดา |
| FR-1.3 | เมื่อเข้าสู่ระบบสำเร็จ ระบบคืน JWT access token ที่ลงลายเซ็นแล้ว (อายุ 60 นาที ปรับได้) ซึ่งบรรจุ `sub`, `email`, `role`, `exp` |
| FR-1.4 | ทุก endpoint ภายใต้ `/api/v1` ยกเว้น `/auth/login` และ `/healthz` ต้องส่ง `Authorization: Bearer <token>` |
| FR-1.5 | token ที่ไม่ถูกต้อง รูปแบบผิด หรือหมดอายุ จะได้รับ `401 Unauthorized` |
| FR-1.6 | การเข้าสู่ระบบที่ล้มเหลวคืน `401` พร้อมข้อความกลาง ๆ ต้องไม่บอกว่าอีเมลนั้นมีอยู่จริงหรือไม่ |
| FR-1.7 | จำกัดการเข้าสู่ระบบไม่เกิน 10 ครั้งต่อ 5 นาทีต่อหนึ่ง IP หากเกินจะคืน `429` โดยเมื่อระบบอยู่หลัง reverse proxy ต้องนับจาก IP จริงของผู้ใช้ ไม่ใช่ IP ของ proxy (ดู `TRUST_PROXY_HEADERS`) |
| FR-1.8 | ฝั่ง client เก็บ token และแนบไปกับทุกคำขอ เมื่อได้รับ `401` ให้ล้าง session และกลับไปหน้าเข้าสู่ระบบ |

### FR-2 — การดูข้อมูลโปรไฟล์

| รหัส | ข้อกำหนด |
|---|---|
| FR-2.1 | `GET /api/v1/me` คืนโปรไฟล์ของผู้เรียก ได้แก่ id ชื่อ นามสกุล URL รูปโปรไฟล์ เบอร์มือถือ อีเมล ที่อยู่ ทักษะ และเวลาปรับปรุง |
| FR-2.2 | ผู้ใช้อ่านได้เฉพาะโปรไฟล์ของตนเอง โดยระบบอ่าน user id จาก token เท่านั้น ไม่อ่านจาก body หรือ query |
| FR-2.3 | ฟิลด์ที่ไม่บังคับและยังว่าง (รูปโปรไฟล์ ที่อยู่) จะคืนค่าเป็น `null` และหน้าจอแสดงตัวแทน เช่น อักษรย่อบนวงกลมสีอ่อนแทนรูปที่ยังไม่มี |
| FR-2.4 | **ผู้ดูแลระบบไม่มีโปรไฟล์พนักงาน** ทุก endpoint ใต้ `/me` คืน `403` เมื่อเรียกด้วย token ที่มี role `admin` และผลลัพธ์ของการเข้าสู่ระบบจะมี `profile` เป็น `null` ทั้งสอง role จึงมีพื้นที่ใช้งานแยกขาดจากกัน |

### FR-3 — การแก้ไขข้อมูลโปรไฟล์

| รหัส | ข้อกำหนด |
|---|---|
| FR-3.1 | ชื่อและนามสกุลกำหนดให้ **อ่านอย่างเดียว (Read-only)** API จะเพิกเฉยต่อค่าที่ส่งมา และหน้าจอแสดงเป็นข้อความธรรมดาพร้อมหมายเหตุว่า "ฝ่ายบุคคลเป็นผู้ดูแล" |
| FR-3.2 | **รูปโปรไฟล์**: `POST /api/v1/me/avatar` (multipart) รองรับ `image/jpeg`, `image/png`, `image/webp` ขนาดไม่เกิน 2 MB โดยตรวจชนิดไฟล์จากเนื้อไฟล์จริง ไม่เชื่อ header ที่ client ส่งมา เก็บไฟล์ด้วยชื่อ UUID ที่สร้างขึ้น และให้บริการผ่าน `/uploads/` |
| FR-3.2.1 | การเปลี่ยนรูปต้องทำผ่าน **หน้าต่าง (modal)** โดยเลือกไฟล์แล้วเห็น **ตัวอย่างรูปก่อน** และจะอัปโหลดจริงก็ต่อเมื่อกดบันทึกเท่านั้น การกดยกเลิกหรือปิดหน้าต่างต้องไม่ส่งอะไรไปยังเซิร์ฟเวอร์และไม่สร้างประวัติ |
| FR-3.3 | **ข้อมูลติดต่อแก้ไขได้ทีละหลายฟิลด์แล้วบันทึกครั้งเดียว**: หน้าจอแสดง `mobile`, `email`, `address` เป็นช่องกรอกพร้อมกันทั้งหมด และมีปุ่มบันทึกเพียงปุ่มเดียว |
| FR-3.3.1 | `PATCH /api/v1/me/contact` ยังรับฟิลด์ชุดย่อยใด ๆ ได้ตามเดิม ฟิลด์ที่ไม่ได้ส่งมาจะไม่ถูกแตะต้อง หน้าจอเลือกส่งทั้งสามฟิลด์ทุกครั้ง |
| FR-3.3.2 | **เซิร์ฟเวอร์เป็นผู้เทียบว่าอะไรเปลี่ยน** ไม่ใช่ฝั่งหน้าจอ โดยเทียบค่าที่ส่งมากับค่าที่เก็บไว้ แล้วบันทึกประวัติเฉพาะฟิลด์ที่เปลี่ยนจริง (ดู FR-3.9) การบันทึกที่ไม่มีอะไรเปลี่ยนเลยต้องไม่สร้างประวัติแม้แต่แถวเดียว |
| FR-3.4 | เบอร์มือถือต้องตรงรูปแบบ E.164 หรือรูปแบบไทย (`+66812345678` หรือ `0812345678`) ความยาว 9–15 หลัก |
| FR-3.5 | อีเมลต้องถูกต้องตามรูปแบบ ยาวไม่เกิน 254 ตัวอักษร และไม่ซ้ำกับผู้ใช้อื่น หากซ้ำจะคืน `409 Conflict` |
| FR-3.6 | ที่อยู่เป็นข้อความอิสระ ยาวไม่เกิน 500 ตัวอักษร |
| FR-3.7 | **ทักษะ**: `PUT /api/v1/me/skills` แทนที่ชุดทักษะของผู้เรียกด้วย id ที่ส่งมา ทุก id ต้องมีอยู่จริงและยังเปิดใช้งานในคลังทักษะ มิฉะนั้นคืน `422` เลือกได้สูงสุด 50 ทักษะต่อคน |
| FR-3.8 | ข้อผิดพลาดจากการตรวจสอบข้อมูลคืน `422` พร้อมรายละเอียดรายฟิลด์: `{"errors": {"mobile": "invalid phone number"}}` |
| FR-3.9 | การบันทึกที่ค่าไม่เปลี่ยนจากเดิมถือเป็น no-op คือสำเร็จแต่ไม่สร้างรายการเปลี่ยนแปลง |

### FR-3.10 — ทักษะส่วนตัวที่พนักงานพิมพ์เอง

| รหัส | ข้อกำหนด |
|---|---|
| FR-3.10.1 | หน้าจอเลือกทักษะต้องมีช่องค้นหา และกรองรายการในคลังตามข้อความที่พิมพ์แบบไม่สนตัวพิมพ์ใหญ่เล็ก |
| FR-3.10.2 | เมื่อข้อความที่พิมพ์ไม่ตรงกับทักษะใดในคลัง ระบบต้องเสนอให้ **เพิ่มเป็นทักษะของตนเอง** ได้ทันที |
| FR-3.10.3 | ทักษะส่วนตัวผูกกับพนักงานคนนั้นเท่านั้น ต้อง **ไม่** ถูกเพิ่มเข้าคลังกลางและต้องไม่ปรากฏในตัวเลือกของผู้อื่น |
| FR-3.10.4 | `PUT /me/skills` รับฟิลด์ `custom_skills` เป็นรายการข้อความ คู่กับ `skill_ids` |
| FR-3.10.5 | ชื่อทักษะส่วนตัวถูกตัดช่องว่างหัวท้าย ยาวไม่เกิน 60 ตัวอักษร และตัดรายการซ้ำแบบไม่สนตัวพิมพ์ใหญ่เล็ก |
| FR-3.10.6 | ชื่อทักษะ **ห้ามมีจุลภาค** ทั้งทักษะส่วนตัวและทักษะในคลัง เพราะประวัติเก็บรายการทักษะเป็นข้อความที่คั่นด้วยจุลภาค หากมีจุลภาคในชื่อ การย้อนกลับจะแยกกลับมาเป็นคนละทักษะ |
| FR-3.10.7 | หากข้อความที่พิมพ์ตรงกับทักษะที่มีอยู่แล้วในคลัง (ไม่สนตัวพิมพ์ใหญ่เล็ก) ระบบต้องถือว่าเป็นการเลือกทักษะนั้นจากคลัง ไม่ใช่สร้างทักษะส่วนตัวซ้ำ |
| FR-3.10.8 | ทักษะส่วนตัวนับรวมในการคำนวณความครบถ้วนตาม FR-7 และปรากฏในประวัติเหมือนทักษะปกติ |

### FR-4 — คลังทักษะ (การตั้งค่า)

| รหัส | ข้อกำหนด |
|---|---|
| FR-4.1 | `GET /api/v1/skills` คืนคลังทักษะที่เปิดใช้งาน (id, ชื่อ, หมวดหมู่) ให้ผู้ใช้ที่ยืนยันตัวตนแล้วทุกคน |
| FR-4.2 | ผู้ดูแลระบบสร้าง เปลี่ยนชื่อ เปลี่ยนหมวดหมู่ และปิดการใช้งานทักษะได้ผ่าน `/api/v1/admin/skills` |
| FR-4.3 | การปิดการใช้งานเป็นแบบ soft delete (`active = false`) ทักษะที่พนักงานเลือกไว้แล้วยังคงอยู่และยังแสดงผล เพียงแต่ไม่ถูกเสนอให้เลือกใหม่ |
| FR-4.3.1 | ทักษะที่ถูกปิดใช้งานแต่พนักงาน **ถืออยู่แล้ว** ต้องส่งกลับมาใน `PUT /me/skills` ได้โดยไม่ถูกปฏิเสธ มิฉะนั้นการปิดทักษะหนึ่งจะทำให้พนักงานแก้ไขทักษะอื่นไม่ได้เลย ส่วนทักษะที่ปิดแล้วและไม่เคยถืออยู่ ยังคงถูกปฏิเสธด้วย `422` |
| FR-4.4 | คลังทักษะถูกใส่ข้อมูลตั้งต้นจาก `migrations/002_seed.sql` ประกอบด้วย Go, React, Flutter, CI/CD และอื่น ๆ โดยการใส่ข้อมูลซ้ำได้โดยไม่เกิดผลข้างเคียง (idempotent) |
| FR-4.5 | ทักษะเป็นรายการแบน **ไม่มีหมวดหมู่** โจทย์กำหนดเพียงรายการทักษะที่ตั้งค่าได้ให้เลือกเท่านั้น |

### FR-5 — ประวัติการเปลี่ยนแปลง

| รหัส | ข้อกำหนด |
|---|---|
| FR-5.1 | ทุกการแก้ไขที่สำเร็จของรูปโปรไฟล์ เบอร์มือถือ อีเมล ที่อยู่ หรือทักษะ จะสร้างรายการเปลี่ยนแปลง: `{id, user_id, field, old_value, new_value, changed_at, changed_by}` |
| FR-5.2 | `GET /api/v1/me/history` คืนรายการของผู้เรียกย้อนหลังตามช่วงเวลาที่ระบบตั้งไว้ เรียงจากใหม่ไปเก่า |
| FR-5.3 | ช่วงเวลาย้อนหลังมาจากการตั้งค่า `history_retention_days` (ค่าโดยปริยาย **7**) และถูกจำกัดให้อยู่ในช่วง 1–365 |
| FR-5.4 | ช่วงเวลาย้อนหลังตั้งค่าได้สองทาง เรียงตามลำดับความสำคัญจากน้อยไปมาก: ตัวแปรสภาพแวดล้อม `HISTORY_RETENTION_DAYS` → ตาราง `settings` ซึ่ง **ผู้ดูแลระบบเท่านั้น** ที่แก้ได้ที่ `/api/v1/admin/settings` |
| FR-5.4.1 | **พนักงานเลือกช่วงเวลาเองไม่ได้** ต้องไม่มีตัวเลือกบนหน้าจอ และ API ต้องไม่รับพารามิเตอร์ที่ใช้ขยายช่วงเวลาได้ เพราะช่วงเวลาที่เปิดให้ดูย้อนหลังเป็นนโยบายขององค์กร ไม่ใช่ความชอบของผู้ใช้ |
| FR-5.5 | หน้าจอแสดงช่วงเวลาที่ใช้อยู่เป็นข้อความ (เช่น "Showing the last 7 days, as set by your administrator") โดยกดเปลี่ยนไม่ได้ และแสดงแต่ละรายการเป็นข้อความที่อ่านเข้าใจได้ ("เบอร์มือถือเปลี่ยนจาก 081… เป็น 089…" พร้อมเวลาแบบสัมพัทธ์) |
| FR-5.8 | **ประวัติต้องแบ่งหน้า** เพราะผู้ใช้ที่แก้ไขบ่อยจะมีรายการยาวจนอ่านไม่ไหว โดย `GET /me/history` รับ `page` และ `per_page` ค่าเริ่มต้น 5 รายการต่อหน้า และจำกัดไม่เกิน 100 เพื่อไม่ให้คำขอเดียวดึงทั้ง log |
| FR-5.9 | ผลลัพธ์ต้องคืน `page`, `per_page`, `total`, `total_pages` เพื่อให้หน้าจอวาดปุ่มเปลี่ยนหน้าได้ และการขอหน้าที่เลยจำนวนจริงต้องคืนรายการว่าง ไม่ใช่ข้อผิดพลาด เพราะถือเป็นลิงก์เก่า ไม่ใช่ความล้มเหลว |
| FR-5.12 | ตัวควบคุมการแบ่งหน้าต้องแสดง **เลขหน้า** ให้กดข้ามไปหน้าที่ต้องการได้โดยตรง ไม่ใช่มีแค่ปุ่มก่อนหน้า/ถัดไป และเมื่อจำนวนหน้ามาก ต้องย่อด้วยจุดไข่ปลาโดยคงหน้าแรก หน้าสุดท้าย และหน้าปัจจุบันพร้อมหน้าข้างเคียงไว้เสมอ |
| FR-5.11 | **ประวัติเป็นข้อมูลอ่านอย่างเดียว** ต้องไม่มีช่องทางใดในระบบที่ย้อนกลับ แก้ไข หรือลบรายการในประวัติ |
| FR-5.6 | ประวัติเป็นแบบเพิ่มได้อย่างเดียว (append-only) ไม่มี endpoint ใดแก้ไขหรือลบรายการ |
| FR-5.7 | การเปลี่ยนทักษะถูกบันทึกเป็นรายการเดียว โดยค่าเก่าและค่าใหม่เป็นชื่อทักษะที่ต่อกันด้วยจุลภาค เพื่อให้อ่านรู้เรื่อง ทั้งทักษะจากคลังและทักษะส่วนตัวแสดงรวมกันโดยไม่แยกแหล่งที่มา |

### FR-6 — ~~ย้อนกลับการแก้ไข~~ (ถอดออกแล้ว)

ฟีเจอร์ย้อนกลับ (undo) ถูกถอดออกตามที่ตกลงกัน ประวัติเป็นบันทึกสำหรับตรวจสอบย้อนหลัง
อย่างเดียว ไม่ใช่เครื่องมือแก้ไขข้อมูล ทั้ง endpoint `POST /me/history/{id}/revert`
และปุ่มบนหน้าจอถูกลบออกทั้งหมด ดู FR-5.11

ผลที่ตามมา: ไฟล์รูปโปรไฟล์เก่าที่ถูกแทนที่แล้วจะถูกลบทิ้งทันทีอีกครั้ง เพราะไม่มีอะไร
ต้องย้อนกลับไปใช้แล้ว ทำให้พื้นที่จัดเก็บไม่บวมขึ้นเรื่อย ๆ

## 6. เกณฑ์การตรวจรับ (Acceptance Criteria)

1. เข้าสู่ระบบด้วย `somchai@example.com` / `Password123!` แล้วเข้าสู่หน้าโปรไฟล์ที่แสดงชื่อ
   ข้อมูลติดต่อ และทักษะตามข้อมูลตั้งต้น
2. ฟิลด์ชื่อและนามสกุลแสดงเป็นข้อความ ไม่ใช่ช่องกรอก และการเรียก `PATCH /me/contact`
   พร้อมคีย์ `first_name` ต้องไม่ทำให้ชื่อที่เก็บไว้เปลี่ยน
3. การแก้ไขเฉพาะเบอร์มือถือต้องไม่กระทบอีเมลและที่อยู่ และสร้างประวัติเพียงหนึ่งแถว
4. การอัปโหลดไฟล์ขนาด 3 MB ถูกปฏิเสธด้วย `422` ส่วนการอัปโหลดไฟล์ PNG ขนาด 500 KB
   ที่ถูกต้องต้องเปลี่ยนรูปโปรไฟล์ทันที
5. การเลือก "Flutter" แล้วบันทึก สร้างประวัติทักษะหนึ่งแถวที่ระบุค่าก่อนและหลัง
5.1 การพิมพ์ "Elixir" ซึ่งไม่มีในคลัง ต้องมีปุ่มให้เพิ่มเป็นทักษะของตนเอง และเมื่อบันทึกแล้ว
    พนักงานคนอื่นต้องไม่เห็น "Elixir" ในตัวเลือกของตน
6. ประวัติแสดงช่วง 7 วันตามค่าเริ่มต้น หน้าจอพนักงานต้องไม่มีปุ่มเลือกช่วงเวลา และเมื่อผู้ดูแล
   เปลี่ยนการตั้งค่าเป็น 30 วัน พนักงานจึงจะเห็นรายการที่เก่ากว่า
7. เมื่อมีประวัติเกิน 20 รายการ หน้าจอต้องแสดงปุ่มเปลี่ยนหน้า และต้องไม่มีปุ่มย้อนกลับ
   (undo) ปรากฏที่ใดเลย
8. ที่ความกว้าง 375 px, 768 px และ 1440 px หน้าจอต้องไม่มีการเลื่อนแนวนอน
9. คำสั่ง `go test ./...` และ `npm test` ต้องผ่านทั้งคู่
10. เข้าสู่ระบบด้วย `admin@example.com` แล้วต้องไปอยู่ที่ `/admin` เห็นคลังทักษะและช่องตั้งค่าจำนวนวัน
    โดยไม่เห็นส่วนใดของโปรไฟล์ และการเปิด `/` ด้วยบัญชีนี้ต้องถูกพากลับมาที่ `/admin`
11. เรียก `GET /api/v1/me` ด้วย token ของ admin ต้องได้ `403`
