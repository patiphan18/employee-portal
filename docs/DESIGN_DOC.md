## 1. สถาปัตยกรรม

```
                    ┌──────────────────────────────┐
  เบราว์เซอร์ ─────▶│  web  (nginx :8080)          │
                    │  React 18 + Vite + Tailwind  │
                    └──────────────┬───────────────┘
                                   │  /api/v1/*  (JSON + JWT)
                                   ▼
                    ┌──────────────────────────────┐
                    │  api  (Go :8000)             │
                    │  chi router                  │
                    │  ├─ middleware: cors, log,   │
                    │  │  recover, auth, ratelimit │
                    │  ├─ api/      HTTP handlers  │
                    │  ├─ service/  กฎทางธุรกิจ     │
                    │  ├─ store/    SQL repository │
                    │  └─ /uploads  ไฟล์รูปโปรไฟล์   │
                    └──────────────┬───────────────┘
                                   │  database/sql (lib/pq)
                                   ▼
                    ┌──────────────────────────────┐
                    │  db  (PostgreSQL 16 :5432)   │
                    └──────────────────────────────┘
```

ระบบประกอบด้วยสามคอนเทนเนอร์ภายใต้ `docker-compose.yml` เดียว โดยฝั่ง API ให้บริการเฉพาะ JSON
และไฟล์ที่อัปโหลด ส่วน nginx ให้บริการ SPA และทำ proxy เส้นทาง `/api` กับ `/uploads` ไปยัง API
ทำให้บนระบบจริงเบราว์เซอร์เห็นเป็น origin เดียว และ CORS จึงเป็นเรื่องของสภาพแวดล้อมพัฒนาเท่านั้น

### 1.1 การแบ่งชั้น (Layering)

| ชั้น | แพ็กเกจ | หน้าที่ | รู้จัก |
|---|---|---|---|
| Transport | `internal/api` | แปลง HTTP เข้า/ออก กำหนด status code จัดการ auth context และบังคับขอบเขตของ role (`RequireAuth`, `RequireEmployee`, `RequireAdmin`) | service |
| Domain | `internal/service` | ตรวจสอบข้อมูล ตรวจจับการเปลี่ยนแปลง บันทึกประวัติ คำนวณความครบถ้วน | store interface |
| Persistence | `internal/store` | คำสั่ง SQL การแปลงแถวข้อมูล ทรานแซกชัน | `database/sql` |
| ใช้ร่วมกัน | `internal/auth`, `internal/config`, `internal/validate` | JWT การเข้ารหัสรหัสผ่าน ตัวแปรสภาพแวดล้อม กฎของแต่ละฟิลด์ | ไม่ขึ้นกับใคร |

ทิศทางการพึ่งพาชี้เข้าด้านในทางเดียว โดย `service` พึ่งพา **interface** ที่ประกาศไว้ใน
`internal/store` (`UserStore`, `SkillStore`, `HistoryStore`, `SettingStore`)
ซึ่งเป็นเหตุผลที่ทำให้ชั้น service ทดสอบได้ด้วย fake ในหน่วยความจำโดยไม่ต้องมีฐานข้อมูลจริง

### 1.2 การตัดสินใจเชิงออกแบบที่สำคัญ

| ลำดับ | การตัดสินใจ | เหตุผล | ทางเลือกที่ไม่เลือก |
|---|---|---|---|
| D1 | ใช้ `net/http` ของ Go ร่วมกับ chi | chi เพิ่มมาจาก stdlib เพียงแค่ routing และ URL param จึงไม่ผูกติดกับเฟรมเวิร์ก | Gin, Echo — หนักเกินความจำเป็นของระบบนี้ |
| D2 | ใช้ `database/sql` กับ SQL ที่เขียนเอง | สคีมามีขนาดเล็ก การเขียน SQL ตรง ๆ ทำให้เห็นความเสี่ยง N+1 ชัดเจน และทำให้คิวรีสำหรับการตรวจสอบย้อนหลังอ่านเข้าใจง่าย | GORM — ซ่อน query plan ในระบบที่เน้นการตรวจสอบย้อนหลัง |
| D3 | JWT แบบไร้สถานะ ไม่มี refresh token | เวอร์ชัน 1 มี token อายุสั้นเพียงชนิดเดียว การทำรายการเพิกถอนต้องใช้สถานะร่วมที่ไม่มีส่วนอื่นต้องการ | session ฝั่งเซิร์ฟเวอร์ |
| D4 | ให้ชั้น service เขียนประวัติ ไม่ใช่ DB trigger | การสร้าง diff ต้องใช้บริบทจากแอปพลิเคชัน เช่น **ชื่อ** ทักษะ (ไม่ใช่ id) และ `changed_by` ซึ่ง trigger ต้องไปค้นหาเอาเองใหม่ | trigger บน UPDATE ของ Postgres |
| D5 | เก็บรูปโปรไฟล์บน volume ไม่ใช่ในฐานข้อมูล | ทำให้ขนาดแถวข้อมูลเล็ก และให้ nginx ส่งไฟล์ได้โดยตรง อีกทั้งเปลี่ยนไปใช้ S3 ได้ภายใต้ interface `Storage` เดิม | คอลัมน์ชนิด `bytea` |
| D6 | ใช้ pointer semantics กับการ patch ข้อมูลติดต่อ | `*string` แยกความต่างระหว่าง "ไม่ได้ส่งมา" กับ "ตั้งเป็นค่าว่าง" ได้ ซึ่งตรงกับสิ่งที่ FR-3.3 ต้องการพอดี | PUT ทั้งอ็อบเจ็กต์ |
| D7 | ใช้ soft delete กับทักษะ | การปิดใช้งานทักษะต้องไม่ลบทักษะนั้นออกจากพนักงานที่เลือกไว้แล้วโดยเงียบ ๆ | hard delete พร้อม cascade |
| D8 | แยกพื้นที่ของสอง role ออกจากกันโดยสิ้นเชิง | ผู้ดูแลเป็นผู้ตั้งค่าระบบ ไม่ใช่พนักงานที่มีโปรไฟล์ การให้ `/me*` เป็นของพนักงานเท่านั้นและ `/admin/*` เป็นของผู้ดูแลเท่านั้น ทำให้ขอบเขตสิทธิ์อ่านออกจาก route ได้ทันที ไม่ต้องไปไล่อ่านเงื่อนไขในหน้าจอ | ให้ผู้ดูแลมีโปรไฟล์ด้วยแล้วค่อยซ่อนเมนูใน UI ซึ่งเป็นการกันแค่เปลือก |
| D16 | คลังทักษะแบ่งหน้าที่ฝั่ง browser ไม่ใช่ที่เซิร์ฟเวอร์ | ต่างจาก audit log ตรงที่คลังทักษะมีขอบเขตจำกัดตามที่ผู้ดูแลสร้าง และหน้าจอโหลดทั้งรายการอยู่แล้วเพื่อนับจำนวนที่เปิดใช้งาน การแบ่งหน้าฝั่งเซิร์ฟเวอร์จึงเพิ่มกลไกโดยไม่ได้อะไรกลับมา ถ้าวันหนึ่งคลังโตมาก การย้ายไปทำฝั่งเซิร์ฟเวอร์เป็นการแก้ที่ชั้น store เหมือนที่ทำกับประวัติ | แบ่งหน้าที่เซิร์ฟเวอร์ตั้งแต่ต้น |
| D15 | ช่วงเวลาย้อนหลังเป็นการตั้งค่าของผู้ดูแล ไม่ใช่ตัวเลือกของผู้ใช้ | ระยะเวลาที่เปิดให้พนักงานดูประวัติตัวเองย้อนหลังเป็นนโยบาย ไม่ใช่ความชอบส่วนตัว การตัดพารามิเตอร์ออกจาก API ด้วย (ไม่ใช่แค่ซ่อนปุ่ม) ทำให้ไม่มีช่องให้ขยายช่วงเองด้วยการยิง URL ตรง | ซ่อนปุ่มแต่เก็บ `?days=` ไว้ ซึ่งยังเลือกได้อยู่ดีด้วย token ปกติ |
| D13 | ให้เซิร์ฟเวอร์เป็นผู้เทียบว่าข้อมูลติดต่อฟิลด์ไหนเปลี่ยน | หน้าจอส่งทั้งสามฟิลด์เสมอ แล้วให้ `Diff()` ที่ชั้น service ตัดสิน ความจริงเรื่อง "ค่าปัจจุบันคืออะไร" อยู่ที่ฐานข้อมูล ถ้าให้ฝั่งหน้าจอเทียบเอง มันจะเทียบกับสำเนาที่อาจเก่าไปแล้ว และยังต้องรู้เรื่องการจัดรูปแบบ (เช่น `081-234-5678` กับ `0812345678` คือค่าเดียวกัน) ซึ่งเป็นกฎของฝั่งเซิร์ฟเวอร์ | ให้หน้าจอส่งเฉพาะฟิลด์ที่คิดว่าเปลี่ยน |
| D14 | เปลี่ยนรูปผ่าน modal ที่มีตัวอย่างก่อนบันทึก | การอัปโหลดทันทีที่เลือกไฟล์ทำให้เลือกผิดแล้วแก้ไม่ได้ และสร้างแถวประวัติที่ผู้ใช้ไม่ได้ตั้งใจ การแยกขั้น "เลือก" ออกจาก "บันทึก" ทำให้ความผิดพลาดมีต้นทุนแค่กดยกเลิก | อัปโหลดทันทีแล้วให้ย้อนกลับทีหลัง ซึ่งตอนนี้ก็ไม่มี undo แล้ว |
| D12 | ประวัติเป็นข้อมูลอ่านอย่างเดียว ไม่มี undo | บันทึกสำหรับตรวจสอบย้อนหลังที่แก้ไขสถานะได้ด้วย จะกลายเป็นเครื่องมือแก้ไขข้อมูลที่เลี่ยงการตรวจสอบปกติ การถอด undo ออกทำให้ประวัติทำหน้าที่เดียวคือบอกว่าเกิดอะไรขึ้น และลบ endpoint ที่เปลี่ยนข้อมูลได้ออกไปหนึ่งจุด | ซ่อนปุ่มแต่เก็บ endpoint ไว้ ซึ่งแย่กว่าเพราะยังเรียกได้ด้วย token ปกติ |
| D10 | เก็บทักษะส่วนตัวไว้คนละตารางกับคลังกลาง | โจทย์บอกว่าให้ "เพิ่มใส่ของตัวเอง" ทักษะที่พนักงานพิมพ์จึงไม่ควรไปโผล่ในตัวเลือกของคนอื่น ถ้าเขียนลงตาราง `skills` ร่วมกัน คลังจะถูกคนทั่วไปแก้โดยอ้อมและหลุดการควบคุมของผู้ดูแล | สร้างรายการในคลังกลางอัตโนมัติ, เก็บเป็นคอลัมน์ `text[]` บน users |
| D11 | ห้ามจุลภาคในชื่อทักษะ | ประวัติเก็บชุดทักษะเป็นข้อความคั่นจุลภาค ถ้าชื่อมีจุลภาคได้ การ undo จะแยกกลับเป็นคนละทักษะ ซึ่งเป็นข้อบกพร่องที่พบจากการรีวิว และการเปิดให้พิมพ์อิสระทำให้โอกาสเกิดสูงขึ้นมาก จึงกันที่ขอบ | เก็บประวัติเป็น JSON array ซึ่งต้องแก้ทั้งการแสดงผลและข้อมูลเดิม |
| D9 | ใช้ react-router-dom แทนการสลับหน้าด้วย state | โจทย์ต้องการ path `/admin` จริง จึงต้องรองรับปุ่ม back, การ bookmark และการ refresh ค้างหน้า ซึ่งการเขียน router เองจะค่อย ๆ กลายเป็นการเขียน router ที่ไม่สมบูรณ์ | สลับคอมโพเนนต์ด้วย state (ไม่มี URL), เขียน router เองจาก History API |

### 2.1 ดัชนี (Indexes)

| ดัชนี | วัตถุประสงค์ |
|---|---|
| `users(email)` แบบ unique | ใช้ค้นหาตอนเข้าสู่ระบบ และบังคับความไม่ซ้ำตาม FR-3.5 |
| `profile_changes(user_id, changed_at DESC)` | รองรับคิวรีประวัติแบบแบ่งหน้า โดยอ่านเพียงช่วงหนึ่งของดัชนีนี้ (`LIMIT`/`OFFSET`) ไม่ต้องสแกนทั้งตาราง |
| `user_skills(skill_id)` | ใช้ค้นย้อนกลับเมื่อมีการปิดใช้งานทักษะ |
| `user_custom_skills(user_id, lower(name))` unique | กันไม่ให้พนักงานคนเดียวมี "Elixir" และ "elixir" พร้อมกัน |
| `skills(active, sort_order)` | ใช้แสดงรายการคลังทักษะ |

### 2.2 ค่าที่เป็นไปได้ของ `profile_changes.field`

`avatar` · `mobile` · `email` · `address` · `skills`

ค่า `old_value` และ `new_value` เก็บเป็นข้อความ โดยเป็นค่าตรงตัวสำหรับข้อมูลเดี่ยว
เป็นรายชื่อทักษะที่เรียงลำดับและต่อกันด้วยจุลภาคสำหรับ `skills` และเป็น URL สำหรับ `avatar`
การเก็บเป็นชื่อแทน id หมายความว่าการเปลี่ยนชื่อทักษะในภายหลังจะไม่ไปเขียนทับสิ่งที่ผู้ใช้เคยเห็น

### 2.3 การย้ายสคีมา (Migrations)

ใช้ไฟล์ SQL ธรรมดาที่มีหมายเลขกำกับ ประมวลผลตามลำดับตอนที่ API เริ่มทำงาน
และบันทึกไฟล์ที่ทำไปแล้วในตาราง `schema_migrations`

| ไฟล์ | เนื้อหา |
|---|---|
| `001_init.sql` | extension, ตาราง, ดัชนี |
| `002_seed.sql` | คลังทักษะ, ค่าตั้งต้นของการตั้งค่า (ใช้ `ON CONFLICT DO NOTHING` จึงรันซ้ำได้) |
| `003_custom_skills.sql` | ลบคอลัมน์ `category` และเพิ่มตาราง `user_custom_skills` |

### 3.2 ลำดับการทำงานของคำขอ — `PATCH /api/v1/me/contact`

1. **Auth middleware** อ่าน `Authorization: Bearer` ตรวจลายเซ็น HS256 และ `exp`
   แล้วใส่ claims ลงใน request context หากไม่ผ่านจะคืน `401`
2. **Handler** แปลง `{mobile?, email?, address?}` ลงในโครงสร้างที่ใช้ `*string`
   ทำให้คีย์ที่ไม่ได้ส่งมายังเป็น `nil` ส่วนการส่ง `""` มาอย่างชัดเจนหมายถึงการล้างค่า
3. **Service** ตรวจสอบเฉพาะฟิลด์ *ที่ส่งมา* (FR-3.4 ถึง FR-3.6) โหลดข้อมูลปัจจุบัน
   แล้วคำนวณ diff ฟิลด์ที่ไม่เปลี่ยนจะถูกตัดทิ้งที่ขั้นนี้ ซึ่งเป็นที่อยู่ของ FR-3.9
4. **Store** รันคำสั่ง `UPDATE` และ `INSERT` ประวัติภายในทรานแซกชันเดียวกัน
   ทำให้เป็นไปไม่ได้ที่โปรไฟล์จะเปลี่ยนโดยไม่มีแถวประวัติกำกับ
5. **Handler** คืนโปรไฟล์ที่อัปเดตแล้วพร้อม `200`

### 3.3 การตรวจจับการเปลี่ยนแปลงและการบันทึกประวัติ

มีฟังก์ชันตัวช่วยเดียวที่ผลิตชุดการเปลี่ยนแปลง:

```go
type Change struct { Field, Old, New string }

func diff(before, after *models.User) []Change
```

ชั้น service เรียก `diff` ทำการอัปเดต แล้วแทรกแถว `profile_changes` หนึ่งแถวต่อหนึ่ง `Change`
ภายในทรานแซกชันเดียวกัน ส่วนทักษะใช้เส้นทางคู่ขนาน (`diffSkills`) ที่แปลง id เป็นชื่อที่เรียงแล้ว
ก่อนเปรียบเทียบ ดังนั้นการสลับลำดับของชุดเดิมจะไม่สร้างรายการเปลี่ยนแปลง

### 3.4 การคำนวณช่วงเวลาย้อนหลัง (FR-5.4)

```go
func (h *History) ResolveDays(ctx context.Context) int
// ลำดับความสำคัญ: settings.history_retention_days → ตัวแปรสภาพแวดล้อม → 7
// แล้วจำกัดให้อยู่ในช่วง [1, 365] โดยไม่รับค่าจากคำขอของผู้ใช้เลย
```

การจำกัดช่วงอยู่ในฟังก์ชันเดียว เพื่อให้ handler การตรวจสอบตอนย้อนกลับ
และงานล้างข้อมูลในอนาคต ไม่มีทางเข้าใจคำว่า "อยู่ในช่วงเวลา" ไม่ตรงกัน

### 3.5 การแบ่งหน้าของประวัติ (FR-5.8)

```
GET /me/history?page=P&per_page=S
  → HistoryCount(user, since)        นับทั้งหมดในช่วงเวลา เพื่อคำนวณ total_pages
  → History(user, since, S, (P-1)*S) ดึงเฉพาะหน้าที่ขอด้วย LIMIT/OFFSET
  → คืน {days, page, per_page, total, total_pages, events}
```

ค่าเริ่มต้นคือ 5 รายการต่อหน้า และ `per_page` ถูกจำกัดไว้ที่ 100 เพื่อไม่ให้คำขอเดียวดึง log ทั้งก้อน และหน้าที่เลยจำนวนจริง
คืนรายการว่างแทนข้อผิดพลาด เพราะลิงก์เก่าไม่ใช่ความผิดของผู้ใช้

เรียงด้วย `changed_at DESC, id DESC` ทำให้ลำดับคงที่แม้สองรายการจะมีเวลาเท่ากัน
ซึ่งจำเป็นสำหรับการแบ่งหน้า มิฉะนั้นรายการเดียวอาจโผล่สองหน้าหรือหายไปเลย

> **หมายเหตุ** — `OFFSET` จะช้าลงเมื่อหน้าลึกมาก ที่ขนาดข้อมูลระดับนี้ยังไม่เป็นปัญหา
> ถ้าในอนาคตประวัติโตมาก ควรเปลี่ยนไปใช้ keyset pagination (คิวรีจาก `changed_at` ของ
> รายการสุดท้าย) ซึ่งเปลี่ยนเฉพาะชั้น store

### 3.6 การอัปโหลดรูปโปรไฟล์

`http.MaxBytesReader` จำกัดขนาด body ไว้ที่ 2 MB ก่อนเริ่มแปลงข้อมูล จากนั้นนำ 512 ไบต์แรก
ไปเข้า `http.DetectContentType` ชนิดใดที่อยู่นอกรายการอนุญาต JPEG/PNG/WebP จะได้ `422`
ไฟล์ถูกเขียนลงเป็น `<uuid><ext>` บน volume ของการอัปโหลด และ URL ที่เก็บคือ `/uploads/<name>`
ไฟล์เดิมถูกลบแบบ best-effort เมื่อมีการอัปโหลดทับ เนื่องจากไม่มี undo แล้วจึงไม่มีอะไร
ต้องย้อนกลับไปใช้ไฟล์เก่า และพื้นที่จัดเก็บไม่บวมขึ้นเรื่อย ๆ
ส่วนแถวประวัติยังเก็บ URL เดิมไว้เป็นบันทึกว่าโปรไฟล์เคยระบุอะไร ไม่ได้รับประกันว่าไฟล์ยังอยู่ ปัจจุบัน interface `Storage` มีการพัฒนาไว้หนึ่งแบบ
(`LocalStorage`) หากจะเพิ่มแบบ S3 ก็ไม่ต้องแตะชั้น service เลย

### 3.7 หมายเหตุด้านความปลอดภัย

| ภัยคุกคาม | มาตรการรับมือ |
|---|---|
| การลองรหัสผ่านจำนวนมาก (credential stuffing) | bcrypt cost 12, ข้อความผิดพลาดกลาง ๆ, จำกัดจำนวนครั้งต่อ IP (FR-1.7) โดยหมายเลข IP มาจาก `X-Real-IP` / `X-Forwarded-For` เมื่อเปิด `TRUST_PROXY_HEADERS` มิฉะนั้นทุกคำขอที่ผ่าน nginx จะถูกนับรวมเป็น IP เดียวกันและผู้ใช้ที่สุจริตจะถูกล็อกออก |
| การปลอม header เพื่อเลี่ยง rate limit | ไม่เชื่อ proxy header เป็นค่าเริ่มต้น และเมื่อเปิดใช้งานจะอ่านรายการ **สุดท้าย** ของ `X-Forwarded-For` ซึ่งเป็นค่าที่ nginx เติมเองด้วย `proxy_add_x_forwarded_for` ไม่ใช่รายการแรกที่ผู้ใช้ส่งมาได้ |
| บัญชีตัวอย่างหลุดขึ้น production | `config.Load` บังคับปิดการสร้างบัญชีตัวอย่างเมื่อ `APP_ENV=production` แม้จะตั้ง `SEED_DEMO_USERS=true` ก็ตาม |
| การขโมย token | อายุ token 60 นาที เก็บไว้ในหน่วยความจำและ `sessionStorage` ไม่ใช่คุกกี้อายุยาว |
| การเข้าถึงข้อมูลผู้อื่น (IDOR) | user id มาจาก claims ใน token เสมอ ไม่มี handler ใดอ่าน user id จากข้อมูลที่ส่งเข้ามา |
| SQL injection | ใช้ parameterised query เท่านั้น |
| ไฟล์อัปโหลดที่เป็นอันตราย | จำกัดขนาด ตรวจชนิดจากไบต์จริง ตั้งชื่อไฟล์ใหม่ ส่งพร้อม `Content-Disposition` และไม่ประมวลผลเป็นสคริปต์ |
| XSS | React หลีกเลี่ยงอักขระพิเศษให้โดยปริยาย และไม่มีการใช้ `dangerouslySetInnerHTML` ที่ใดเลย |
| ความลับรั่วไหล | รับความลับจากตัวแปรสภาพแวดล้อม และบนระบบจริงจะปฏิเสธ secret ค่าเริ่มต้นที่ติดมากับโค้ด |

### 4.1.1 เส้นทางและการกันตาม role

| เส้นทาง | ผู้เข้าถึงได้ | พฤติกรรมเมื่อ role ไม่ตรง |
|---|---|---|
| `/login` | ผู้ที่ยังไม่เข้าสู่ระบบ | ถ้ามี session อยู่แล้วจะถูกพาไปหน้าแรกของ role ตัวเอง |
| `/` | พนักงาน | ผู้ดูแลถูกพาไป `/admin` |
| `/admin` | ผู้ดูแล | พนักงานถูกพาไป `/` |
| เส้นทางอื่น | — | พาไปหน้าแรกของ role หรือ `/login` |

`RequireRole` เลือก **พาไปหน้าที่ถูกต้อง** แทนการขึ้นข้อความ "ไม่มีสิทธิ์" เพราะการที่ผู้ใช้
มาอยู่ผิดหน้าคือการเดินผิดทาง ไม่ใช่ความพยายามบุกรุก ส่วนการกันจริงอยู่ที่ฝั่งเซิร์ฟเวอร์
ซึ่งคืน `403` เสมอไม่ว่าหน้าจอจะทำอะไร

เนื่องจาก role มาพร้อมกับ session การกู้คืน session หลังรีเฟรชจึงต้องเรียก `GET /auth/me`
ให้ได้ role ก่อนวาดหน้าแรก มิฉะนั้นผู้ใช้จะเห็นหน้าผิดวาบหนึ่งก่อนถูกพาไปหน้าที่ถูกต้อง

### 4.2 การจัดการสถานะ

ไม่ใช้ Redux สถานะที่มาจากเซิร์ฟเวอร์อยู่ใน hook สองตัว (`useProfile`, `useHistory`)
ซึ่งดูแลชุดสถานะ fetch/loading/error ของตนเอง ส่วนสถานะการยืนยันตัวตนอยู่ใน context เดียว
`EditableField` แต่ละตัวเก็บข้อความร่างของตัวเองไว้ภายใน และส่งค่าขึ้นไปเมื่อกดบันทึกเท่านั้น
นี่คือสิ่งที่ทำให้ข้อมูลติดต่อทั้งสามฟิลด์แก้ไขแยกจากกันได้ (FR-3.3) โดยไม่ต้องมีอ็อบเจ็กต์ฟอร์มร่วมกัน

หลังการแก้ไขสำเร็จ hook ทั้งสองตัวจะดึงข้อมูลใหม่ ประวัติจึงสะท้อนการแก้ไขนั้นทันที

### 4.3 หน้าจอแบบ Responsive (FR-8)

| ช่วงความกว้าง | Tailwind | การจัดวาง |
|---|---|---|
| ไม่เกิน 640 px | base | คอลัมน์เดียว เรียงการ์ดตัวตน ข้อมูลติดต่อ ทักษะ และประวัติลงมาตามลำดับ ปุ่มใช้ `w-full` ช่องกรอกใช้ `h-11` |
| 641–1024 px | `sm:` / `md:` | กริดการ์ดสองคอลัมน์ โดยการ์ดตัวตนกินพื้นที่ทั้งสองคอลัมน์ |
| ตั้งแต่ 1025 px | `lg:` | `lg:grid-cols-[320px_1fr]` — แถบข้างตัวตนแบบติดหนึบ คู่กับเนื้อหาที่เลื่อนได้ คอนเทนเนอร์ใช้ `max-w-7xl` |

ดังนั้นการจัดวางสำหรับจอแคบจึงเป็นค่าโดยปริยาย ไม่ใช่ทางเลือกสำรอง

### 4.4 สถานะของการโต้ตอบ

ทุกตัวควบคุมที่เปลี่ยนแปลงข้อมูลจะมีสี่สถานะ ได้แก่ ว่าง กำลังบันทึก (แสดงตัวหมุนและปิดการใช้งาน)
สำเร็จ (toast สีเขียว) และผิดพลาด (ข้อความในบรรทัดของฟิลด์ พร้อมคงค่าที่พิมพ์ไว้เพื่อให้แก้ซ้ำได้)
ระบบไม่ใช้การอัปเดตแบบมองโลกในแง่ดี (optimistic) เพราะถือว่าคำตอบจากเซิร์ฟเวอร์คือความจริง
ซึ่งเป็นเรื่องสำคัญเมื่อเซิร์ฟเวอร์จัดรูปแบบหมายเลขโทรศัพท์ให้เป็นมาตรฐาน

## 7. การนำขึ้นใช้งาน

คำสั่ง `docker compose up --build` จะเริ่ม `db` (พร้อม healthcheck) ก่อน ตามด้วย `api`
(ซึ่งรอ healthcheck แล้วจึงรัน migration และใส่ข้อมูลตั้งต้น) และปิดท้ายด้วย `web`
อิมเมจของ API เป็น build สองขั้นบน `golang:1.26-alpine` ที่ผลิตไบนารีแบบ static ไว้บน `alpine`
ส่วนอิมเมจของเว็บ build ด้วย Node แล้วส่งมอบ bundle บน `nginx:alpine`
ทั้งไฟล์อัปโหลดและไฟล์ฐานข้อมูลอยู่บน named volume การ build ใหม่จึงไม่ทำให้ข้อมูลหาย

### 7.1 ข้อจำกัดที่ทราบ

- ตัวจำกัดจำนวนคำขออยู่ภายในโปรเซส จึงเป็นการจำกัดต่ออินสแตนซ์ ไม่ใช่ทั้งระบบ
  และ map ที่เก็บสถิติยังไม่ถูกล้าง key ที่หมดอายุ (ควรแก้ก่อนเปิดให้เข้าถึงจากอินเทอร์เน็ตจริง)
- ประวัติยังไม่ถูกตัดทิ้งตามอายุ ช่วงเวลาที่ตั้งค่าคุมเพียงสิ่งที่แสดงผล ยังต้องมีงาน pruning
- การแบ่งหน้าใช้ `OFFSET` ซึ่งช้าลงเมื่อหน้าลึกมาก (ดู 3.5)
- ไม่มี refresh token เมื่อครบ 60 นาที ผู้ใช้ต้องเข้าสู่ระบบใหม่
- รูปโปรไฟล์ที่อยู่บน volume ภายในเครื่องจะไม่รองรับการขยายเป็นหลายโหนด หากไม่มีพื้นที่จัดเก็บร่วมกัน
- ประวัติไม่เคยถูกลบออก งานล้างข้อมูลตามช่วงเวลาเป็นสิ่งที่ต้องทำในอนาคต
